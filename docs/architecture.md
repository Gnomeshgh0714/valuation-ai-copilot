# 某国际地产咨询机构估价部 AI 助手 · 应用架构

> 日期：2026-08-21
> 背景：为简历「AI 应用经验」段提供工程细节支撑
> 项目定位：估价师手动处理 Excel 底稿 + 扫描合同耗时久的痛点 → AI 助手实现 Excel 自动解析、合同信息抽取、可比案例检索、报告智能生成

---

## 一、业务痛点

| 痛点 | 现状 | 后果 |
|---|---|---|
| Excel 底稿处理 | 估价师手动从 xlsm 提数，公式嵌套深、外部链接失效多 | 单项目数天 |
| 扫描合同录入 | 关键字段（租金、面积、租期）人工肉眼识别录入 | 单份合同 10-30 分钟，且易错 |
| 可比案例查找 | 凭经验翻阅历史报告，无结构化检索 | 漏查、错配常见 |
| 报告撰写 | 数据从 Excel 复制到 Word，重复劳动 | 数值一致性靠人工三审 |

**目标**：单项目人工耗时从数天压缩至数小时，OCR 关键字段人工复核率从 100% 降至 20%。

## 二、整体架构（四层）

```
┌─────────────────────────────────────────────────────┐
│  用户层：估价师上传 Excel / 扫描合同 → Web 前端       │
└─────────────────────────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  接入层：FastAPI（异步）→ Celery + Redis 任务队列    │
│  · 大文件底稿异步处理，避免同步阻塞                   │
└─────────────────────────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  AI 服务层（4 个核心模块）                           │
│  ├─ Excel 解析引擎（openpyxl + LibreOffice headless）│
│  ├─ 文档抽取（PaddleOCR + PP-StructureV3）          │
│  ├─ RAG 检索（BGE-M3 + BM25 + Reranker + HyDE）     │
│  └─ 报告生成 Agent（Qwen2.5-14B + Function Calling）│
└─────────────────────────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  存储层：PostgreSQL + pgvector（业务数据 + 向量）    │
│        MinIO（原始文件）                             │
└─────────────────────────────────────────────────────┘
```

**部署**：本地化部署（Qwen2.5-14B AWQ 4bit 量化 + vLLM），满足客户数据合规要求——机密数据不出内网。

## 三、四大核心模块

### 模块 1 · Excel 解析引擎

**核心难点**：xlsm 底稿含大量跨表公式与外部链接，`openpyxl` 默认只读公式字符串；`data_only=True` 读的是 Excel 上次保存时缓存的计算结果，**外部链接失效时缓存是脏数据**。

**解决方案**：
- **LibreOffice headless 强制重算**：把 xlsm 丢给 LibreOffice 后台进程，让它重新计算公式，绕过 Excel 缓存
- **外部链接失效治理**：单个项目文件曾发现 **145 个外部链接**，失效链接读 XML 缓存值并标记可信度，高不确定字段进人工复核队列
- **Schema 匹配分级**：表头指纹匹配覆盖 80% 已知模板；新模板用 LLM 兜底（成本可控）
- **数据校验**：Pydantic 模型校验值域、跨表一致性（面积 × 单价 = 总价），业务错配自动拦截

### 模块 2 · 文档抽取（OCR + 表格还原）

**技术栈**：PaddleOCR（文字识别）+ PP-StructureV3（版面分析 + 表格结构还原）+ LLM 后处理

**关键设计**：
- **本地化部署**：客户合同含商业机密，必须用开源模型本地跑，不能用云端 OCR API
- **关键字段双通道校验**：OCR 识别 + 正则规则 + 跨字段交叉验证（如"租金 = 单价 × 面积"）
- **低置信度降级**：识别置信度 < 阈值的字段自动进人工复核队列，而不是强行输出错误结果

### 模块 3 · RAG 可比案例检索

**完整 pipeline**：
```
可比案例库 → 按"案例"整 chunk → BGE-M3 向量化 → pgvector 存储
                                                      ↓
查询 → HyDE 查询改写 → 硬过滤（区域/物业类型/面积）→ 混合检索（向量 + BM25，RRF 融合）
                                                      ↓
                                          bge-reranker 重排取 top5
```

**为什么是混合检索而不是单向量**：
- 向量检索擅长语义相似（"工业园区厂房" ≈ "制造业仓储用房"）
- BM25 擅长精确匹配专有名词、编号、地址（"苏州工业园区苏虹东路 XX 号"）
- 单独用任何一个都会漏，RRF 融合后 Recall@5 ≥ 85%

**幻觉控制**：
- 强制引用 chunk id，所有数值必须匹配原文
- 低置信度结果标记"需人工审核"，不直接进入报告
- 数值强校验：AI 输出的租金、面积、资本化率必须与检索结果原文一致

### 模块 4 · 报告生成 Agent

**架构**：分章节多步 Agent
```
Planner（生成报告大纲）→ 逐章节 Worker（背景/区位/实物/权益/市场/测算）→ Critic（数值校验）→ 组装 docx
```

**核心原则**：「**计算确定性留给代码，语言灵活性留给 LLM**」
- 所有数字（租金、面积、DCF 结果、资本化率）从 PostgreSQL 直接注入 prompt
- LLM 只负责组织语言，不负责计算或回忆数值
- 从机制上消灭"AI 瞎编数字"的幻觉

**部署**：Qwen2.5-14B + Function Calling，AWQ 4bit 量化，vLLM continuous batching，单张 RTX 4090 可支撑 10-20 并发。

## 四、三个关键技术难点与突破

### 难点 1 · Excel 公式重算与外部链接脏数据治理

**矛盾**：估价师的 xlsm 底稿依赖大量跨表公式 + 外部链接（链接到其他底稿、市场数据表），链接失效时 Excel 显示的是上次缓存的"假值"，直接读会污染整个测算链路。

**突破**：
- 用 LibreOffice headless 作为"独立计算引擎"，强制重算所有公式
- 对 145 个外部链接逐一排查，失效的读 XML 缓存并打"可信度分"
- 低可信度字段不直接进下游，进人工复核队列——**宁可慢，不可错**

### 难点 2 · RAG 在"垂直领域 + 专有名词密集"场景的检索准确率

**矛盾**：估价领域专有名词密集（"转售资本化率"、"收益还原法"、"比较法修正系数"），纯向量检索容易把"写字楼资本化率"召回成"工业厂房资本化率"；纯 BM25 又无法理解"高新区厂房"和"工业园区制造用房"是同一类。

**突破**：
- 向量 + BM25 混合检索，RRF 融合，各补短板
- HyDE 查询改写：让 LLM 先生成一段"假设的可比案例描述"，再用这段描述去检索，把"用户问题"翻译成"领域语言"
- bge-reranker 精排：粗排 top-50 → 精排 top-5，兼顾召回与精度

### 难点 3 · 大模型在"数值强约束"场景的幻觉控制

**矛盾**：估价报告里的每一个数字都必须有出处、能回溯，但 LLM 天然倾向"流畅地编一个合理的数字"——这是估价业务的**红线**。

**突破（三层防线）**：
1. **数据注入**：所有数值从 PostgreSQL 直接注入 prompt，不让 LLM 凭印象写
2. **强制引用**：输出必须附 chunk id，无引用的句子直接拒收
3. **数值强校验**：Critic Agent 单独跑一遍，把 AI 输出的每个数字与数据库比对，不一致立即打回重生成

## 五、技术选型理由

| 组件 | 选择 | 不选 | 理由 |
|---|---|---|---|
| 向量库 | **pgvector** | Milvus / Qdrant | 几万条案例量级 pgvector 够用，避免多运维一套独立向量库 |
| Embedding | **BGE-M3** | OpenAI Embedding | 中文效果优于 OpenAI，且支持本地化（数据合规硬要求） |
| LLM | **Qwen2.5-14B** | GPT-4 / Claude | 本地化部署 + 中文表达符合国内估价报告语言习惯 |
| 推理引擎 | **vLLM** | TGI / llama.cpp | continuous batching 吞吐高，单 4090 撑 10-20 并发 |
| OCR | **PaddleOCR + PP-StructureV3** | 阿里云 / 腾讯云 OCR | 数据合规，且表格结构还原精度满足估价合同 |
| 异步框架 | **Celery + Redis** | RQ / Dramatiq | 生态成熟，大文件必须异步 |
